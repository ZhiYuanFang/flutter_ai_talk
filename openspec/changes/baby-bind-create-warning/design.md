## Context

当前宝宝绑定页面已支持“绑定已有宝宝”和“创建新宝宝”双路径，但在创建路径中缺少家庭协同提示，用户可能在家人已创建宝宝时重复创建。与此同时，页面与入口文案仍存在“绑定宝宝ID”的表达，和产品语义“绑定宝宝”不一致，易造成理解偏差。

本次变更仅涉及前端 UI 交互与文案，不改变 `bindwx` / `auto_save` API 调用方式，不引入新依赖。

## Goals / Non-Goals

**Goals:**
- 在用户尝试创建新宝宝前给出明确提醒，提示优先使用绑定功能。
- 将“绑定宝宝ID”文案统一为“绑定宝宝”。
- 保持现有创建/绑定流程与接口行为兼容。

**Non-Goals:**
- 不新增后端校验接口或服务端去重策略。
- 不改变宝宝资料模型字段与保存逻辑。
- 不改动首页历史、WS、设置其他模块业务逻辑。

## Decisions

1. **在创建动作前增加确认提示，而非创建后回滚**
   - 方案 A（采用）：点击“创建新宝宝”提交前弹出提醒/确认，用户可取消并切换到绑定模式。
   - 方案 B（不采用）：先创建再提示用户撤销，存在已创建成功的副作用与清理成本。

2. **统一文案层替换“绑定宝宝ID”为“绑定宝宝”**
   - 方案 A（采用）：对绑定页面按钮、标题与引导文案进行一致化替换。
   - 方案 B（不采用）：仅改部分入口会导致同屏语义不一致。

3. **保持 API 层不变**
   - 原因：需求是交互引导与文案一致性，不涉及协议或字段变更；可降低回归风险。

## Risks / Trade-offs

- [风险] 提示频率过高影响创建效率 → [缓解] 仅在“创建提交”关键路径弹出一次，文案简洁。
- [风险] 文案修改遗漏导致体验不一致 → [缓解] 针对绑定页面相关字符串做一次全量检查。
- [取舍] 仅做前端提醒无法从系统层杜绝重复创建 → [说明] 当前版本先解决误操作主要来源，后续可评估服务端幂等/归并策略。

## Migration Plan

- 无数据迁移。
- 发版后前端直接生效。
- 回滚策略：回退到本次变更前的 UI 版本即可，不影响已有数据。

## Open Questions

- 提示文案是否需要加入“联系家人获取宝宝编号/二维码”等更具体的绑定指引，可在产品评审后追加。
