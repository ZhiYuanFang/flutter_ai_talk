## Context

当前 iOS 发布能力集中在单一工作流中，通过 `release_mode` 与多组输入参数组合实现多目标分发。该方式在 GitHub Actions `workflow_dispatch` 的静态表单限制下，无法做到真正的动态字段展示，导致：

- 参数可见性与生效范围不直观，容易误填；
- 模式分支逻辑持续膨胀，维护成本上升；
- 分发目标（蒲公英、TestFlight、ASC）语义边界混杂。

本次变更聚焦 CI 工作流架构重组，不改动 Flutter 业务代码。关键约束：

- `ad-hoc` 必须支持蒲公英自动上传，且上传失败必须阻断构建；
- `appstore` 入口仅上传到 ASC，不自动提审、不自动发布；
- 保持现有签名/导出链路稳定，避免破坏既有证书与描述文件配置。

## Goals / Non-Goals

**Goals:**

- 提供三个语义清晰的发布入口：`ad-hoc`、`testflight`、`appstore`。
- 将公共构建步骤抽象为可复用核心流程，减少重复与配置漂移。
- 明确三条分发链路的输入、鉴权、执行与失败策略。
- 将失败行为标准化：分发步骤失败默认使对应工作流失败。

**Non-Goals:**

- 不修改 iOS 应用功能、签名证书内容或 Apple 开发者账号结构。
- 不在本次变更中引入“自动提审/自动发布 App Store”。
- 不实现跨平台（Android）分发编排改造。

## Decisions

### Decision 1：采用“3 个入口工作流 + 1 个复用核心工作流”

- 选择：
  - 入口：`build-ios-adhoc.yml`、`build-ios-testflight.yml`、`build-ios-appstore.yml`
  - 核心：`ios-build-core.yml`（`workflow_call`）
- 原因：
  - 在 GitHub 原生表单不支持动态联动的前提下，按入口拆分可获得最清晰的操作体验；
  - 通过复用核心流程，避免三份工作流复制粘贴。
- 备选方案：
  - 保留单工作流 + 强校验：体验改善有限；
  - 完全三份独立实现（无复用）：后续维护成本高。

### Decision 2：按入口固定分发目标与导出语义

- `ad-hoc`：固定 `ad-hoc` 导出 + 蒲公英上传。
- `testflight`：固定 `app-store` 导出 + TestFlight 上传。
- `appstore`：固定 `app-store` 导出 + ASC 上传（upload only）。

原因：入口语义与分发结果一一对应，降低“同一入口多模式”带来的认知负担。

### Decision 3：蒲公英上传失败采用硬失败策略

- 选择：`ad-hoc` 分发步骤返回非零即失败整条 workflow。
- 原因：团队明确要求“分发结果可用”作为 ad-hoc 流程完成标准。
- 备选方案：
  - 降级为 warning：会产生“构建成功但分发失败”的灰色状态，不符合目标。

### Decision 3.1：蒲公英成功日志不要求安装短链

- 选择：上传成功后仅输出可追溯字段（构建号、版本、上传状态、错误码为空等），不强制输出安装短链/二维码。
- 原因：团队明确“不需要安装短链输出”，避免暴露额外分发链接并降低日志冗余。
- 备选方案：
  - 输出短链/二维码：可用但非当前运营必需信息。

### Decision 4：ASC 语义限定为上传，不触发提审/发布

- 选择：`appstore` 仅执行上传到 App Store Connect 的步骤。
- 原因：减少自动化误操作风险，并与组织发布流程（人工审核发布节奏）一致。
- 备选方案：
  - 上传后自动提审：需要额外审批与发布策略，超出本次范围。

### Decision 5：Secret 最小暴露与按入口分层

- `ad-hoc` 入口仅依赖构建签名 + 蒲公英凭据；
- `testflight/appstore` 入口依赖 ASC API Key；
- 核心流程仅消费其被调用入口显式传入的 secrets。

原因：降低凭据误用与权限扩散风险。

### Decision 6：TestFlight 内部测试组参数改为可选

- 选择：`testflight` 入口不强制填写内部测试组；未填写时执行“仅上传 TestFlight”路径。
- 原因：满足快速上传验证场景，减少触发表单阻塞。
- 备选方案：
  - 强制填写测试组：分发更完整但会抬高使用门槛。

### Decision 7：旧单入口立即退场

- 选择：不设过渡窗口，旧入口在本次变更上线时即退场（删除或改为失败提示并指向新入口）。
- 原因：避免双轨并行带来的错误入口选择与维护成本。
- 备选方案：
  - 保留 1~2 周过渡：兼容性更好，但会延长混乱期。

## Risks / Trade-offs

- [Risk] 工作流文件数量增加 → **Mitigation**：将可复用逻辑收敛到 `ios-build-core.yml`，入口仅保留参数映射与调用。
- [Risk] 旧入口立即退场导致部分同学短期找不到新入口 → **Mitigation**：在文档与仓库公告同步发布新入口映射，并在旧入口文件保留清晰跳转提示（短期）。
- [Risk] 蒲公英 API 抖动导致 ad-hoc 频繁失败 → **Mitigation**：上传步骤增加有限重试与错误分类日志。
- [Risk] 三入口参数命名不一致 → **Mitigation**：建立统一命名约定（`flutter_version`、`build_name`、`build_number` 等公共字段一致）。

## Migration Plan

1. 新增核心复用工作流并抽取公共构建步骤。
2. 新增三个入口工作流，分别绑定分发目标与固定语义。
3. 在 `ad-hoc` 入口接入蒲公英上传并启用失败阻断策略。
4. 立即退场旧单入口工作流，并将入口映射写入文档。
5. 更新 README 与 [docs/github-ios-ipa.md](docs/github-ios-ipa.md)，补充蒲公英凭据在 Repository Secrets 的配置说明。

回滚策略：若新入口在生产使用中出现阻断问题，可临时回退到旧单入口工作流；核心脚本保持独立提交，便于按文件级回滚。
