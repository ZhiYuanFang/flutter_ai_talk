# Design: disable-default-input-autofocus

## Context

当前项目输入入口分布在多个页面和弹层中，部分输入框会在页面进入或返回时被自动聚焦，导致键盘自动弹出。该行为会打断浏览流程、遮挡内容并造成“误进入编辑态”的体感问题。此次改动是跨页面的输入交互一致性治理，涉及路由切换、页面生命周期、弹层展示与焦点状态管理。

## Goals / Non-Goals

**Goals:**

- 建立统一的“进入/返回页面不自动聚焦输入框”规则。
- 确保键盘仅由用户显式点击输入框触发。
- 保持现有表单功能、校验逻辑、提交流程不变。
- 覆盖页面与弹层输入场景并提供可回归的验收标准。

**Non-Goals:**

- 不调整后端 API 或数据结构。
- 不重做现有 UI 样式或表单布局。
- 不移除用户主动聚焦后弹出键盘的正常行为。

## Decisions

### 决策 1：采用“默认无焦点进入”策略并在路由返回时显式清理焦点

- 方案：页面构建与恢复可见时，确保不存在被动持有焦点的输入框；在路由返回后进行一次焦点清理。
- 原因：可直接消除“返回即弹键盘”的体验问题。
- 备选：仅修复个别页面。
  - 未选原因：风险是遗漏场景，行为不一致。

### 决策 2：输入框聚焦仅允许由显式用户动作触发

- 方案：禁用 `autofocus` 默认行为，并在必要处延后焦点申请到明确用户交互后。
- 原因：确保键盘弹出符合用户意图。
- 备选：保留自动聚焦并通过延迟隐藏键盘规避。
  - 未选原因：会产生闪烁与额外状态复杂度。

### 决策 3：保留现有提交链路，不改变业务回调

- 方案：仅改焦点触发时机，不变更 `onSubmitted`、按钮提交、表单校验与错误提示流程。
- 原因：减少回归面，保证业务行为稳定。
- 备选：同步重构提交逻辑。
  - 未选原因：超出本次范围，风险过高。

## Risks / Trade-offs

- [风险] 部分场景依赖旧自动聚焦实现“快速输入” → **缓解**：保留显式点击即可聚焦，并在验收中确认操作成本可接受。
- [风险] 路由返回时焦点清理时机不当可能影响动画或弹层状态 → **缓解**：统一在安全时机执行（如 post-frame）并限定作用域。
- [风险] 多弹层叠加时焦点状态复杂 → **缓解**：弹层关闭时统一清理当前输入焦点，避免残留。

## Migration Plan

1. 第一阶段：梳理输入页面和弹层，识别默认聚焦来源。
2. 第二阶段：按页面批量移除/禁用自动聚焦，并接入统一焦点清理逻辑。
3. 第三阶段：执行高频路径回归（首页、登录、注册、设置与编辑弹层）。
4. 回滚策略：若出现严重输入可用性问题，按页面恢复原焦点行为并保留日志比对。

## Open Questions

- 是否存在必须保留自动聚焦的特殊无障碍场景？
- Web 端是否需要与移动端完全一致，或保留浏览器原生焦点行为？
- 是否需要增加埋点统计“返回后误弹键盘”问题改善幅度？
