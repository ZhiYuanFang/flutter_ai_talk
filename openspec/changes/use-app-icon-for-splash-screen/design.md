# Design: use-app-icon-for-splash-screen

## Context

当前启动视觉由原生启动页 + Flutter 冷启动遮罩 + `/splash` 占位页构成。现状中，中心图标使用 `splash_logo`，与桌面 App 图标存在差异，导致品牌识别不连续。

约束如下：

- 需要复用现有启动链路，不改变 `ColdStartBootstrap` 的阻塞顺序与最短展示时长。
- 已有能力 `startup-splash-gradient-visual` 规定了背景渐变与标语表现，本次仅调整中心图标来源和绘制方式。
- 图标资源应与桌面图标同源，避免后续双轨维护。

## Goals / Non-Goals

**Goals:**

- 启动遮罩与 `/splash` 占位页的中心图标统一切换为桌面主图标同源资产。
- 图标渲染为圆形并尽量填满容器，视觉上不出现明显内缩留白。
- 保持背景渐变、标语与启动时序不变。
- 输出可验证的验收点，便于 QA 在 Android/iOS 双端回归。

**Non-Goals:**

- 不改动桌面图标主资源本身（仅复用）。
- 不新增动画节奏、品牌文案或路由跳转逻辑。
- 不引入新的第三方依赖或构建流程变更。

## Decisions

1. **统一图标来源到桌面主图标资产**
   - 决策：启动页图标引用与桌面图标一致的主源资产（项目内单一来源）。
   - 原因：消除品牌割裂，降低资源维护成本。
   - 备选方案：继续保留独立 `splash_logo`。未采纳原因：长期会继续产生视觉漂移。

2. **通过圆形裁剪 + `BoxFit.cover` 实现“圆形填满”**
   - 决策：在启动图标容器中使用圆形裁剪（如 `ClipOval` 或等价圆角裁剪），图像采用 `BoxFit.cover` 填满。
   - 原因：`cover` 能保证圆形容器被图像完整覆盖，避免默认 `contain` 造成边缘留白。
   - 备选方案：仅放大 `contain` 尺寸。未采纳原因：不同分辨率下仍可能出现边距不一致。

3. **同一组件策略覆盖冷启动遮罩与 `/splash`**
   - 决策：抽取/复用同一图标展示样式，确保两处表现一致。
   - 原因：避免两端样式漂移，减少后续维护分叉。
   - 备选方案：分别在两处单独实现。未采纳原因：重复代码且一致性难保证。

4. **不改变启动时序，仅替换视觉层**
   - 决策：所有改动限定在 UI 展示层，不触及 bootstrap 与导航门禁。
   - 原因：规避冷启动时序回归风险，确保变更可控。

## Risks / Trade-offs

- **[风险] 桌面图标主源非正方形或安全区过大导致裁剪后主体偏小** → **缓解**：在实现前检查源图比例；必要时通过容器尺寸和对齐策略微调。
- **[风险] `cover` 可能裁掉边缘关键元素** → **缓解**：以当前主图标为基准做双端截图验收，确认裁剪区域可接受。
- **[风险] 两处页面实现不一致** → **缓解**：统一组件或常量，避免重复样式参数。

## Migration Plan

- 本变更为前向兼容的 UI 调整，无数据迁移。
- 发布策略：随常规版本发布。
- 回滚策略：若出现品牌或适配问题，可回滚至原 `splash_logo` 渲染实现，不影响业务数据与接口。

## Open Questions

- 当前桌面主图标在超小屏设备上的可视占比是否需要额外微调（仅影响视觉，不影响本次需求达成）。
