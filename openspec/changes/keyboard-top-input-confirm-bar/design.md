# Design: keyboard-top-input-confirm-bar

## Context

当前应用在多个页面和弹层中分散使用 `TextField`/`TextFormField`，输入焦点行为、提交方式与键盘联动不一致：
- 部分页面在聚焦后被键盘顶起，导致布局跳动；
- 部分场景依赖系统键盘回车提交，部分依赖页面按钮提交；
- 弹层场景（如设置对话框、记录编辑）在键盘弹出时可用高度变化明显，影响可操作性。

该变更是跨模块的 UI 交互统一改造，涉及应用壳层、输入组件、页面级提交流程和弹层输入流程，需要先明确统一技术方案再进入实现。

## Goals / Non-Goals

**Goals:**

- 建立统一输入桥接层，接管“焦点输入 → 键盘上方确认条 → 回填目标输入框 → 触发提交”的标准流程。
- 在受管控输入场景中避免主界面因键盘弹出被整体顶起。
- 保持现有业务逻辑和表单能力（校验、密码态、只读态、历史按钮行为）不被破坏。
- 支持页面输入与弹层输入的统一体验，并可按场景渐进接入。

**Non-Goals:**

- 不改动后端 API、鉴权协议或数据模型。
- 不重构现有所有表单组件样式，仅统一输入与确认交互行为。
- 不引入新的第三方输入法 SDK。

## Decisions

### 决策 1：采用“全局输入桥接控制器 + 键盘顶部确认条”而非逐页面独立实现

- 方案：在应用壳层引入统一输入桥接状态（当前焦点目标、临时输入值、确认回调、显示策略），由统一的键盘顶部确认条组件渲染。
- 原因：
  - 可避免每个页面重复处理键盘高度、焦点迁移和提交联动；
  - 能统一回填与确认语义，降低行为分叉；
  - 便于后续扩展（禁用场景、脱敏显示、分析埋点）。
- 备选：逐页面/逐弹层独立改造。
  - 未选原因：维护成本高，易产生行为不一致，难以全量回归。

### 决策 2：受管控页面/弹层默认关闭“键盘顶起布局”，改为确认条承接输入

- 方案：在纳入范围的页面与弹层中，统一使用“界面稳定布局 + 键盘顶部确认条”策略。
- 原因：目标是解决视觉跳动并统一确认路径。
- 备选：保留 `resizeToAvoidBottomInset` 默认行为，仅做局部修补。
  - 未选原因：无法从根本上统一体验，仍会出现页面级差异。

### 决策 3：确认动作采用“双写回 + 显式提交回调”

- 方案：点击“确定”时，先将确认条文本写回目标 `TextEditingController`，再调用场景注册的 `onConfirm`（可映射现有 `onSubmitted` 或按钮提交方法）。
- 原因：保证目标输入框值与业务提交流程一致，避免“显示值与提交值”分离。
- 备选：仅触发提交回调，不强制写回输入框。
  - 未选原因：易导致页面字段与提交参数不一致，影响可追溯性。

### 决策 4：对密码类输入执行脱敏展示策略

- 方案：当目标输入框为密码场景时，确认条左侧文本区默认显示脱敏内容（如 `••••`），仅内部保存原值用于回填与提交。
- 原因：避免在键盘顶部额外暴露敏感信息。
- 备选：明文展示以提升可见性。
  - 未选原因：安全与隐私风险不可接受。

## Risks / Trade-offs

- [风险] 焦点在对话框/底部弹层切换时可能出现目标引用失效 → **缓解**：桥接层按 `FocusNode` 生命周期自动解绑，确认前验证目标仍挂载。
- [风险] 全局接管可能影响现有回车提交流程 → **缓解**：保留原 `onSubmitted` 兼容路径，按场景逐步切换到统一 `onConfirm`。
- [风险] 多行输入场景对“确定=换行还是提交”认知不同 → **缓解**：在规格中明确多行场景默认提交语义，必要时支持场景级覆盖。
- [权衡] 统一交互会增加初期接入工作量 → **收益**：后续输入场景扩展成本更低、体验一致性更高。

## Migration Plan

1. 第一阶段：接入高频页面（首页文本输入、登录、注册）并验证键盘不顶起与确认回填闭环。
2. 第二阶段：接入弹层场景（设置弹窗、记录编辑、数值事件备注）。
3. 第三阶段：接入其余输入入口（宝宝绑定、宝宝资料编辑等）并完成全量回归。
4. 回滚策略：保留原输入提交流程开关，发生严重问题时可按页面关闭桥接接入恢复旧行为。

## Open Questions

- 是否需要对“仅数字输入”场景提供独立确认条样式（例如更紧凑布局）？
- 是否需要引入埋点统计（确认条展示率、确认点击率、取消率）以评估体验收益？
- 在 Web 端是否沿用同一确认条行为，还是保持键盘 Enter 优先？
