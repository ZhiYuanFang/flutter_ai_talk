## Context

App 现状中对同一标识存在两套表述：实现层使用 `deviceNo`，用户界面中部分位置也直接展示“设备ID/设备”，造成语义割裂。产品希望用户侧只感知“宝宝ID”，而设备语义仅保留在协议与内部实现。

该需求属于跨页面文案一致性治理，涉及绑定页、设置页、可能透传到 UI 的错误提示与空状态提示，但不涉及 API 字段与数据结构调整。

## Goals / Non-Goals

**Goals:**
- 用户可见文案统一为“宝宝ID”语义。
- 清理用户可见层中“设备ID/设备/deviceNo”等术语。
- 保持现有接口与内部逻辑稳定，避免引入兼容风险。

**Non-Goals:**
- 不修改后端协议字段名（继续使用 `deviceNo` / `device_no`）。
- 不进行全量变量/文件/类名重构（如 `DeviceNoNotifier` 重命名）。
- 不修改业务流程（绑定、创建、登录、WS 机制保持不变）。

## Decisions

1. **分层治理：只改用户可见层文案**
   - 采用：仅替换 UI 文案、toast、用户可见错误文案。
   - 不采用：连同内部命名一起改，工作量大且易引入回归。

2. **协议字段保持 `deviceNo`**
   - 采用：请求参数和响应解析不变，确保后端兼容。
   - 不采用：改成 `babyId` 需后端联动与灰度，超出本次范围。

3. **以“展示文本清单 + 全量检索”双保险**
   - 采用：先列举用户可见入口，再通过关键字检索回归，降低遗漏。
   - 不采用：只做局部人工改动，容易残留旧术语。

## Risks / Trade-offs

- [风险] 某些内部异常信息被 UI 直接透传，遗漏替换 → [缓解] 覆盖 repository 中可能弹给用户的错误字符串。
- [风险] 改文案后上下文不自然（如“清除设备缓存”） → [缓解] 改为用户语义（如“清除宝宝ID缓存”或“清除本地宝宝绑定信息”）。
- [取舍] 保留内部 `deviceNo` 命名会产生代码语义差异 → [说明] 以稳定性优先，后续可单独发起内部重构变更。

## Migration Plan

- 无数据迁移。
- 前端发版即生效。
- 若出现争议，可快速回退文案改动，不影响数据与接口。

## Open Questions

- “设备缓存”在用户文案中统一为“宝宝ID缓存”还是“宝宝绑定信息缓存”，需产品做最终术语定稿。
