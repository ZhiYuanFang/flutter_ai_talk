## Context

当前账号入口中“注册账号”与登录流程耦合，缺少独立注册页面与明确的信息分层；同时注册表单未强制二次密码确认，容易出现用户输入错误后才在登录阶段暴露问题。该变更主要涉及 Flutter 路由、登录页跳转动作、注册页表单结构与本地校验提示，并要求视觉风格与现有登录页保持一致。

约束：
- 继续复用现有账号注册接口与参数约定，不引入后端契约变更。
- 与现有 UI 规范保持一致，避免出现与登录页不一致的色彩、字体与间距。
- 以最小改动实现可回归、可测试的注册路径。

## Goals / Non-Goals

**Goals:**
- 点击“注册账号”后进入独立注册页面（非当前页内临时区域）。
- 注册页新增“确认密码”字段，提交前执行一致性校验。
- 校验失败时给出明确错误提示并阻止提交。
- 注册页布局、控件样式、交互反馈与登录页保持统一风格。
- 保持现有登录流程与注册 API 可用性。

**Non-Goals:**
- 不修改后端注册接口语义或新增认证协议。
- 不引入短信验证码、图形验证码、邀请制等新注册策略。
- 不重构整套账号系统状态管理，仅覆盖本次注册入口与表单体验。

## Decisions

1. 采用命名路由（或现有路由管理体系）新增独立注册页
- 决策：在现有 Router 配置中新增注册页面路由，由登录页“注册账号”按钮跳转。
- 原因：可测试性强、页面职责清晰、后续可独立扩展注册流程。
- 备选方案：在登录页内嵌展开注册表单。
- 未选原因：页面复杂度上升，且难以保证与登录页风格一致与可维护性。

2. 在客户端表单层增加确认密码校验
- 决策：注册提交前校验 `password == confirmPassword`，不一致则显示错误并禁用本次提交。
- 原因：尽早反馈，减少无效请求并优化用户体验。
- 备选方案：仅依赖后端校验。
- 未选原因：反馈延迟、错误定位不直观。

3. 样式复用登录页组件/主题令牌
- 决策：优先复用登录页已使用的通用输入框、按钮和间距规范，必要时抽取共享样式。
- 原因：确保视觉一致性并降低重复代码。
- 备选方案：为注册页单独实现一套样式。
- 未选原因：高概率造成风格漂移，增加维护成本。

4. 错误提示策略
- 决策：字段级错误（确认密码不一致）+ 页级轻量提示（如已有统一 Toast/SnackBar 机制时复用）。
- 原因：字段级提示可直接指向问题，页级提示用于补充整体提交状态。

## Risks / Trade-offs

- [Risk] 路由改动影响现有导航返回行为（例如返回栈异常）
  → Mitigation：为“登录→注册→返回登录”添加手工与自动化回归用例，明确 `push`/`pop` 语义。

- [Risk] 样式复用不完整导致注册页与登录页存在细微差异
  → Mitigation：对比关键视觉元素（标题、输入框、按钮、页边距、背景）并在评审中附对照截图。

- [Risk] 本地校验与后端错误文案不一致造成用户困惑
  → Mitigation：统一错误文案基调；本地文案聚焦“确认密码不一致”，后端错误沿用现有通道展示。

## Migration Plan

1. 新增注册页路由并接入登录页入口跳转。
2. 在注册页表单中加入确认密码字段与校验逻辑。
3. 对齐登录页视觉样式并补充必要共享组件引用。
4. 增加/更新测试（路由跳转、密码一致性校验、样式关键断言）。
5. 灰度发布（如有渠道策略则按既有策略），观察注册失败率与用户反馈。

回滚策略：
- 若发现严重回归，可在客户端快速回滚到上一版本；代码层面可临时恢复原注册入口行为并关闭新路由入口。

## Open Questions

- 当前“注册账号”在各端（Android/iOS/Web）是否统一使用同一入口文案与交互？若不一致，是否本次一并统一。
- 注册字段是否已有“显示/隐藏密码”交互规范，注册页是否需与登录页完全同款实现。
- 是否已有可复用的表单校验文案国际化 key，避免新增硬编码文案。
