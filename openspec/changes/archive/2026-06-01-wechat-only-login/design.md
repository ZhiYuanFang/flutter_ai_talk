## Context

当前仓库里，`LoginScreen` 仍以设备号输入框 + `signInWithDeviceNo()` 作为真实登录主流程，微信登录按钮仅为未开放占位；与此同时，微信授权链路（移动端 `fluwx` / Web OAuth 回调 / `RemoteAuthRepository.signInWithWeChat()`）已经基本存在，但在 UI 上被关闭。另一个约束是，`SignInChannel.device` 不只是登录来源标记，还被 `RemoteSettingsRepository.saveBaby()` 用来决定是否调用 `POST /device/app/api/user/save`，因此本变更不能把所有 `device` 概念简单删除。

## Goals / Non-Goals

**Goals:**

- 让登录页与产品目标一致：仅提供微信登录入口，并以微信授权作为唯一交互式登录方式。
- 移除客户端对外暴露的设备号登录能力，包括仓储接口、页面提交流程、引导文案和 Web 中“请使用胖宝号登录”的回退逻辑。
- 保持微信登录成功后的会话建立、`deviceNo` 缓存、主页跳转与现有业务链路兼容。
- 为旧安装和历史数据保留必要兼容：已持久化的 `device` 渠道值可以继续被读取，但新版本不得再写入新的设备号登录会话。

**Non-Goals:**

- 不修改网关 `POST /device/app/api/login` 的微信登录契约，也不要求服务端立即下线 `POST /device/app/api/device_login`。
- 不在本变更中重构 `deviceNo` 作为业务标识在历史、画像、绑定等功能中的使用。
- 不在本变更中统一 `RemoteSettingsRepository.saveBaby()` 的所有渠道保存策略；只处理删除设备号登录后必须明确的兼容行为。

## Decisions

1. **登录能力与数据标识分离**  
   - **决策**：仅移除“设备号登录能力”，不移除 `deviceNo` 作为已登录后业务标识的存在。微信登录成功后的响应若返回 `deviceNo`，仍按现有逻辑缓存并供历史、画像等接口使用。  
   - **理由**：代码中 `deviceNo` 已深入后续业务接口；本次产品要求是去掉设备号登录，而非抹除设备号业务模型。  
   - **备选**：同步去除所有 `deviceNo` 相关逻辑——改动面过大且超出需求。

2. **删除公开设备号登录入口，但保留短期兼容读取**  
   - **决策**：从 `AuthRepository` 对外接口和 `LoginScreen` UI 中移除 `signInWithDeviceNo()` 这条产品能力；`SignInChannel.device` 与其持久化解析暂时保留一版兼容旧安装，直到后续确认 `saveBaby` 分支可以统一。  
   - **理由**：这样可以满足“用户不能再触发设备号登录”，同时避免直接破坏已经依赖旧渠道值的画像保存分支。  
   - **备选**：立即删除 `SignInChannel.device` 与相关分支——需要同步调整 `saveBaby()` 接口策略，风险更高。

3. **微信回调结果必须贯通到登录页**  
   - **决策**：Web `WeChatOAuthCallbackScreen` 继续负责解析回调 query 并返回 `/login`，但 `LoginScreen` 不再清理残留微信 OAuth 数据；若检测到待消费的微信授权结果，应直接触发微信登录流程或允许用户点击唯一微信按钮继续完成。移动端则直接调用现有微信 SDK 客户端取码。  
   - **理由**：当前 Web 登录页主动清空 OAuth 结果，等于在产品层阻断微信登录。  
   - **备选**：在回调页直接完成登录——可行，但会把登录页状态与回调页状态耦得更深，不利于统一入口。

4. **错误展示围绕微信链路统一收敛**  
   - **决策**：登录页所有失败提示统一围绕微信授权/微信登录缺少配置来表述，不再出现“请输入胖宝号”“请使用胖宝号登录”“默认使用胖宝号登录”等文案。保留 `WX_LOGIN_CODE` 仅作为开发/联调兜底，不作为用户可见说明主路径。  
   - **理由**：避免产品表述和真实能力冲突。  
   - **备选**：保留设备号文案作为隐藏调试入口——会导致需求回退，且增加理解成本。

5. **README 与 OpenSpec 同步声明 breaking change**  
   - **决策**：文档中明确当前仅支持微信登录；设备号登录章节改为历史说明或移除，并标注这是客户端 breaking change。  
   - **理由**：现有 README 明确写着“默认胖宝号登录”，如果不改，后续实现会与使用说明冲突。  
   - **备选**：只改代码不改文档——不满足规格可追溯要求。

## Risks / Trade-offs

- **[Risk] 微信登录在部分环境仍未完全配好，去掉设备号入口后可能导致无法登录** → 在实现前先校验移动端 AppId / Web OAuth 配置，并保留开发联调用 `WX_LOGIN_CODE` 兜底。  
- **[Risk] 旧用户本地仍存 `SignInChannel.device`，而 `saveBaby()` 分支继续依赖它** → 本变更保留旧值解析，但不再新增写入；后续再单独决定是否统一保存接口。  
- **[Risk] Web 回调与登录页状态衔接不顺，出现回调后仍需重复操作** → 在 spec 中明确回调返回后登录页必须继续消费授权结果，并以集成测试覆盖。  
- **[Risk] 公开接口删除影响现有调用方或测试** → 先全文收敛调用点，确认仓库内只有登录页使用设备号登录，再删除接口并同步更新测试/文档。

## Migration Plan

1. 先更新规格与实现，将登录页入口切到微信，并删除设备号登录的公开调用路径。  
2. 发布后，新安装用户只能走微信登录；旧安装若已登录，现有 token、`deviceNo` 与业务数据继续可用。  
3. 保留一版对旧 `sign_in_channel == device` 的读取兼容，避免影响已落地的画像保存逻辑。  
4. 若线上发现微信配置不完整，可通过回滚客户端版本恢复设备号登录入口；服务端接口无需同步回滚。

## Open Questions

- Web 登录页在拿到待消费 OAuth code 后，是自动发起 `signInWithWeChat()` 还是保留用户手动点击唯一微信按钮，产品更偏好哪种体验？
- `RemoteSettingsRepository.saveBaby()` 后续是否要彻底移除 `device` 分支，统一到微信/通用保存链路？这可能需要后端接口进一步确认。
- 是否需要保留隐藏的开发调试入口（例如仅 debug 模式允许设备号登录），还是要求所有构建形态都完全移除？
